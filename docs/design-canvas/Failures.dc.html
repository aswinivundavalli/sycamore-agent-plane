Failure modes and recovery

Every failure mode has a defined response and automated test coverage. Three rules apply throughout: preserve the record, never infer what cannot be verified, and never resume work without an explicit decision.

Failure mode
System response
Operator experience
Control plane terminated, including kill -9
Agents continue under their detached runners. On restart, each event log resumes from its last committed offset once process identity is verified.
A brief reconnection notice, then every run exactly as it was. The timeline records the re-attachment.
Agent lost during the outage
With no exit record and no live process, the run is marked interrupted. Partial work is committed to its branch.
Surfaced for a decision. Restart resumes the agent's original session with full context.
Agent completed during the outage
The exit record is reconciled on restart; verification runs as normal.
The run appears ready for review.
Outage during launch or verification
During launch, the run is marked interrupted rather than relaunched, since the agent may already have begun. Verification is idempotent and simply re-runs.
A restart decision, or a test result moments later.
Agent error or spend cap reached
Marked failed, with partial work preserved for inspection. Budgets apply per run, so a restart receives only the remaining allowance.
A clear failure reason, such as “Budget cap reached”, alongside the work so far.
Agent stalled or looping
Flagged as stalled after a configurable silence. Past the run-time ceiling, the process group is terminated and the run marked failed.
Escalated in the attention ranking, then a timeout reason.
Concurrent or duplicate requests
Every action is a compare-and-set on the run's current state; exactly one request succeeds.
Duplicates receive a precise conflict response; nothing happens twice.
Outage between merge and record
The merge is written before it is recorded. Retrying is a no-op, because the branch is already contained in the target.
The retry succeeds, with no duplicate merge commit.
Uncommitted changes on the target
The merge is declined. When the target is not checked out, merges are composed in Git's object store and never touch the working copy.
An actionable message naming the branch and the next step.
Unresolved conflict markers
Git would merge them as clean text, so every branch is scanned for markers before merge.
The affected files are named, and merge stays disabled until resolved.
Orphaned worktrees
Released on accept, reject and stop. A periodic sweep removes any worktree whose run has ended or is unknown, then prunes Git metadata.
Live disk usage is always visible in the header.
